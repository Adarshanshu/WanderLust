WANDERLUST PROJECT - COMPLETE REBUILD GUIDE
===========================================

This guide describes how to rebuild the current WanderLust rental-listing
website from an empty folder. It includes the application structure, setup,
database, authentication, image hosting, search, categories, maps, reviews,
deployment, and common errors. Do the steps in order.


1. WHAT THE WEBSITE DOES
------------------------

WanderLust is a server-rendered accommodation listing app. Visitors can browse
stays, search by text and stay type, and see a map on each listing page.
Registered users can create listings, edit or delete their own listings, and
write reviews. Listing photos uploaded through the form go to Cloudinary.
MongoDB Atlas stores users, listings, reviews, and Express login sessions.

Main technologies:
- Node.js and Express 5
- MongoDB Atlas and Mongoose
- EJS templates with ejs-mate layouts
- express-session, connect-mongo, Passport, passport-local,
  passport-local-mongoose
- Multer with a Cloudinary upload-stream storage adapter
- Bootstrap, Font Awesome, and custom CSS
- A Google Maps iframe using each listing's location and country


2. INSTALL THE TOOLS
--------------------

Install Node.js 24 LTS (or a supported Node version at least 20.8), npm, and a
code editor. Create an empty project directory and open a terminal in it.

Initialize the project and install runtime packages:

    npm init -y
    npm install express mongoose ejs ejs-mate dotenv express-session connect-mongo passport passport-local passport-local-mongoose method-override multer cloudinary

Set package.json to CommonJS and add scripts similar to:

    "type": "commonjs",
    "scripts": {
      "start": "node app.js"
    }

Use the package-lock.json generated by npm. Run `npm install` after cloning or
copying the project. The project uses `require(...)` syntax throughout.

Important dependency details:
- connect-mongo 6 is CommonJS-imported as
  `require("connect-mongo").default` in this project.
- Cloudinary SDK v2 is imported with
  `require("cloudinary").v2`.
- The older multer-storage-cloudinary package declares a Cloudinary v1 peer
  dependency. This project avoids that npm dependency conflict by implementing
  Multer's small storage interface directly with Cloudinary's upload_stream.
  Do not add the old adapter back unless its Cloudinary v2 compatibility and
  peer dependency are fixed.

also define the same endpoints in app.js.


4. SET UP MONGODB ATLAS AND CLOUDINARY
--------------------------------------

MongoDB Atlas:
1. Create an Atlas project and cluster.
2. Create a database user with a strong password.
3. Add the deployment host's outbound IP addresses to Atlas Network Access.
   For local work, allow your current development IP. Avoid opening the
   database to every IP for a production deployment.
4. Copy the application's MongoDB connection string. Use the WanderLust
   database name in the URI. URL-encode special characters in the database
   username or password.

Cloudinary:
1. Create a Cloudinary account.
2. From its dashboard, obtain the cloud name, API key, and API secret.
3. Keep the API secret private. Never put it in browser JavaScript, commit it,
   or paste it into a public issue.

Create a local .env file in the project root. Use placeholders while following
this guide; fill in your own values locally:

    NODE_ENV=development
    ATLASDB_URL=mongodb+srv://DB_USER:URL_ENCODED_PASSWORD@YOUR_CLUSTER.mongodb.net/WanderLust?retryWrites=true&w=majority
    SESSION_SECRET=replace-with-a-long-random-secret
    CLOUD_NAME=your-cloudinary-cloud-name
    CLOUD_API_KEY=your-cloudinary-api-key
    CLOUD_API_SECRET=your-cloudinary-api-secret

Generate a session secret locally with Node if needed:

    node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"

Paste the generated value into .env. Do not use the example phrase as a real
production secret. Add these entries to .gitignore:

    .env
    node_modules/

The app loads .env during development. Production hosts should provide the
variables in their environment-variable settings; NODE_ENV=production skips
dotenv loading. Production must define ATLASDB_URL and SESSION_SECRET.


5. DEFINE THE MONGOOSE MODELS
-----------------------------

models/user.js:
- Make a Mongoose user schema with a required email.
- Apply passport-local-mongoose. It adds username/password hashing and the
  methods Passport uses for registration and authentication.
- Export the User model.

models/listing.js:
- Fields: title (required), description, image, price, location, country,
  category, reviews (array of Review ObjectIds), and owner (User ObjectId).
- Store image as an object with `filename` (Cloudinary public ID) and `url`
  (Cloudinary secure URL). Give it a default image URL for listings without an
  uploaded file.
- Category enum values used by the filters:
  `hotels`, `homes`, `villas`, `beach`, `mountain`, `cabins`, `lake`,
  `apartments`.
- Add a `findOneAndDelete` post hook that deletes all reviews referenced by a
  deleted listing.
- Export the Listing model.

models/review.js:
- Fields: required owner (User ObjectId), comment, rating (1 through 5), and
  createdAt (default current date).
- Export the Review model.

Avoid a Mongoose default category of `homes` if old records need to be inferred
from their title and description. A default would mask the missing category on
existing records.


6. BUILD CLOUDINARY STORAGE FOR MULTER
--------------------------------------

In cloudConfig.js:
1. Load `cloudinary.v2` and Node's crypto module.
2. Configure Cloudinary from CLOUD_NAME, CLOUD_API_KEY, CLOUD_API_SECRET.
3. Export a Multer storage object with `_handleFile` and `_removeFile` methods.
4. In `_handleFile`, call `cloudinary.uploader.upload_stream` with folder
   `wanderlust/listings`, a random UUID public_id, and allowed formats jpg,
   jpeg, png, webp, gif. Pipe Multer's `file.stream` into that upload stream.
5. In the callback, pass Multer an object with:
   - filename: Cloudinary result.public_id
   - path: Cloudinary result.secure_url
   - size: Cloudinary result.bytes
6. In `_removeFile`, call `cloudinary.uploader.destroy(file.filename, ...)` and
   forward success or error to Multer's callback.

In app.js, create Multer with this storage object, allow only image/jpeg,
image/png, image/webp, image/gif, and set a 5 MB file-size limit. Convert
Multer errors into a flash message and redirect to the new-listing form.
The multipart form's file input must be named `imageFile` to match
`upload.single("imageFile")`.

On listing creation, if `req.file` exists, save `req.file.filename` and
`req.file.path` in the listing's image object. Otherwise use the optional image
URL form field. The Cloudinary secret must remain server-side.


7. CONNECT MONGOOSE AND CONFIGURE PERSISTENT SESSIONS
----------------------------------------------------

At the beginning of app.js, load dotenv outside production before reading
environment variables. Import Express, Mongoose, express-session, connect-mongo,
Passport, the models, Multer, and middleware.

Database/session order:
1. Read `process.env.ATLASDB_URL`; stop with a clear error if missing.
2. Read `process.env.SESSION_SECRET`. Require it in production. A development
   fallback can be used only for local work.
3. Start one Mongoose connection and keep its promise:

       const dbConnectionPromise = mongoose.connect(dbUrl);

4. Require connect-mongo's CommonJS default export:

       const MongoStore = require("connect-mongo").default;

5. Build the Express session store from the same Mongoose MongoClient. Wait for
   the Mongoose promise before asking the connection for its client:

       MongoStore.create({
         clientPromise: dbConnectionPromise.then(
           () => mongoose.connection.getClient()
         ),
         collectionName: "sessions",
         ttl: 7 * 24 * 60 * 60
       })

6. Configure express-session with the stable SESSION_SECRET, store above,
   `resave: false`, and `saveUninitialized: false`.
7. Set cookie maxAge to seven days, httpOnly true, sameSite `lax`, and secure
   true only in production.
8. In production, set `app.set("trust proxy", 1)` before session middleware so
   secure cookies work when HTTPS terminates at the hosting provider's proxy.
9. Install middleware in this order: method-override/body parser/static files;
   session; flash; Passport initialize; Passport session; locals middleware.
10. Start `app.listen(process.env.PORT || 8080)` only after the database
    connection promise resolves. Log a useful error and exit nonzero if
    MongoDB cannot connect.

Do not create two MongoStore objects and do not put the session secret directly
in source code. Keep SESSION_SECRET unchanged across deployments; changing it
invalidates existing signed cookies.


8. ADD AUTHENTICATION AND ACCESS-CONTROL MIDDLEWARE
--------------------------------------------------

Configure Passport LocalStrategy with `User.authenticate()`. Set
`passport.serializeUser(User.serializeUser())` and
`passport.deserializeUser(User.deserializeUser())`.

Create these helpers in middleware.js:
- `isLoggedIn`: if not authenticated, save the original URL in the session,
  flash an error, and redirect to /login; otherwise call next().
- `saveRedirectUrl`: copy the saved URL into res.locals before Passport login.
- `flash`: provide success/error one-time messages through the session.
- `isListingOwner`: load the listing, return 404 if missing, require its owner
  to equal the logged-in user's ID, then expose the listing in res.locals.
- `isReviewOwner`: verify the listing contains the review ID, load the review,
  require its owner to match the logged-in user, and return 404/redirect on
  invalid or unauthorized requests.

Never rely on hiding an edit/delete button for authorization; enforce ownership
in the route middleware too.


9. IMPLEMENT THE HTTP ROUTES
----------------------------

Use these routes in app.js (or move them to mounted Express routers):

GET  /listings
  Load/populate listings. Read query string `q` and `category`. Search
  case-insensitively across title, description, location, and country. Filter by
  one of the allowed category values. For legacy records with no category,
  infer a display category from title/description keywords. Render
  listings/index.ejs with listings and current search values.

GET  /listings/new
  Require login and render listings/new.ejs.

POST /listings
  Require login, then run upload middleware. Create the listing from form
  fields, saved Cloudinary image or URL, category, and req.user._id. Save, flash
  success, and redirect to /listings.

GET  /listings/:id
  Load listing, populate owner, reviews, and each review owner. Render
  listings/show.ejs. Return 404 if the listing does not exist.

GET  /listings/:id/edit
  Require login and listing ownership. Render edit form with listing and its
  stored or inferred category.

PUT  /listings/:id
  Require login and owner. Update listing fields from req.body.listing, flash,
  redirect to its detail page.

DELETE /listings/:id
  Require login and owner. Delete listing; model hook removes its reviews.

POST /listings/:id/reviews
  Require login. Create review with req.user._id, append its ID to listing,
  save both, flash, redirect to listing detail.

DELETE /listings/:id/reviews/:reviewId
  Require login and review ownership. Remove review ID from listing, delete
  review, flash, redirect.

GET/POST /signup
  Render signup form; register with passport-local-mongoose, log in new user,
  flash, redirect.

GET /login and POST /login
  Render login form. Authenticate with Passport, preserve the saved redirect
  URL, flash errors/success.

POST /logout
  Call Passport logout, flash, redirect.

In Express 5, async route errors should reach error handling middleware or be
caught and passed to next(error). Add a final not-found and error handler when
hardening the app.


10. BUILD THE PAGE TEMPLATES AND FRONT END
------------------------------------------

views/layouts/boilerplate.ejs:
- HTML document, responsive metadata, page title.
- Load Bootstrap CSS/JS, Font Awesome, /CSS/style.css.
- Include navbar, flash messages, rendered body, footer, and shared JS.

views/includes/navbar.ejs:
- Links to Explore and Become a host, auth links or user/logout controls.
- Center a GET form to /listings. Include a text field named `q`, a category
  select named `category` with all icon categories, and a submit button.
- Populate values from searchQuery/searchCategory when rendered on /listings.

views/listings/index.ejs:
- Render full-row category buttons for All stays, Hotels, Homes, Villas,
  Beach stays, Mountain stays, Cabins, Lake stays, Apartments.
- Render listing cards. Put each card's category and searchable text in data
  attributes so listing-filters.js can filter the current result set.
- Load /js/listing-filters.js after the cards.

public/js/listing-filters.js:
- Clicking a category button filters cards in the browser and sets active/
  aria-pressed state. Combine the category with the current keyword. Update the
  empty-state message when nothing is visible.

views/listings/new.ejs and edit.ejs:
- Include title, description, stay type, location, country, price, and image
  URL. The create form additionally has an optional multipart image input
  named `imageFile`, `enctype="multipart/form-data"`, and supported image
  accept types. The edit form can change the URL and category.
- Use field names that match the handlers, including `listing[title]` on edit.

views/listings/show.ejs:
- Show listing photo/details, owner actions, review form/list, and map after
  the reviews. Build a map search query from encoded location and country.
  Include an Open in Google Maps link. The marker is at the matched place or
  area; it is not an exact property pin unless the listing stores a precise
  address.

views/users/signup.ejs and login.ejs:
- Create forms that POST username/email/password and username/password to the
  corresponding auth endpoints.

public/CSS/style.css:
- Define responsive layout, navbar search, full-row categories on desktop,
  listing cards, details, map, auth, review, and flash-message styles. Allow
  category row horizontal scrolling on small screens.

public/js/script.js:
- Add Bootstrap form validation behavior. Do not count this client-side check
  as server-side validation; validate submitted fields in the app too.


11. ADD THE LOCATION MAP
------------------------

For each listing detail page:
1. Join location and country with a comma.
2. URL-encode the combined string before placing it into the map URL.
3. Render an iframe with a useful title, loading="lazy", and a fixed responsive
   wrapper height. Put the map section after the reviews list.
4. Add a separate link to open the same search in Google Maps.

The app currently uses a Google Maps query iframe and Maps search link without
storing coordinates. A city/town value maps to that place, not a private exact
street address. If exact map pins are later required, add latitude/longitude
fields and a deliberate geocoding provider rather than geocoding every page
view.


12. CREATE AND SEED SAMPLE LISTINGS
-----------------------------------

Put sample listing objects in init/data.js and export them as an array. Include
title, description, image URL/object, price, location, country, and optionally
category. In init/index.js connect to MongoDB and insert the sample data.

The current seed script calls `deleteMany({})` before inserting. This is
destructive: only run it against a disposable development database. Never aim
that script at production Atlas data. Prefer a seed script that inserts only
when the collection is empty, or that uses a separate development database.
The old sample script hardcodes a local MongoDB URI; change it to use the
development connection variable before running it with Atlas.


13. RUN LOCALLY
---------------

From the project root:

    npm install
    npm start

The app connects to ATLASDB_URL first, then starts listening on PORT or 8080.
Open `http://localhost:8080/listings`.

First use:
1. Sign up from /signup.
2. Log in if you are not automatically logged in after signup.
3. Use Become a host to create a listing.
4. Test one listing with an image upload and one with an image URL.
5. Open a listing, inspect its map, add a review, edit/delete your listing.
6. Use navbar text search, category selector, and category icons.
7. Verify a second user cannot edit or delete the first user's listing/review.

The package's current `npm test` script is only a placeholder that exits with
an error. Add real automated tests before treating it as a test suite.


14. DEPLOYMENT CHECKLIST
------------------------

1. Push source code and package-lock.json to the deployment service.
2. Configure a Node runtime compatible with the package versions (the project
   currently declares Node 24.13.0 in package.json).
3. Set the build/install command to `npm install` and start command to
   `npm start`.
4. Add these environment variables in the host dashboard:
   - NODE_ENV=production
   - ATLASDB_URL=your Atlas connection string
   - SESSION_SECRET=a newly generated long random secret
   - CLOUD_NAME=your Cloudinary cloud name
   - CLOUD_API_KEY=your Cloudinary API key
   - CLOUD_API_SECRET=your Cloudinary API secret
5. In Atlas Network Access, permit the deployment service's outbound IPs.
   Confirm the Atlas database user has access to the WanderLust database.
6. Confirm Cloudinary credentials are correct and the account can upload.
7. Configure the host's health check to use a route that returns success, if
   the platform requires one. Add a simple health endpoint if needed.
8. Deploy over HTTPS. The app sets secure cookies and trusts one proxy hop in
   production. Do not disable secure cookies just to hide a proxy setup issue.
9. Restart/redeploy after changing environment variables.
10. Test signup, login, refresh while logged in, logout, listing create, image
    upload, search, map, and review flows on the deployed URL.


15. COMMON ERRORS AND FIXES
--------------------------

"MongoStore.create is not a function"
  For connect-mongo 6 in this CommonJS app, import
  `require("connect-mongo").default`. Do not create multiple stores.

"Identifier 'MongoStore' has already been declared"
  Remove duplicate imports/declarations. Keep one MongoStore import and one
  MongoStore.create(...) store passed into express-session.

"ATLASDB_URL is required" or Mongoose cannot connect
  Define ATLASDB_URL in the host settings (or local .env), check the URI,
  URL-encode special password characters, verify the Atlas database user, and
  check Atlas Network Access.

"SESSION_SECRET is required in production"
  Set SESSION_SECRET in deployment environment settings. Do not rely on the
  local development fallback in production.

Login works locally but disappears after deploy/refresh
  Ensure connect-mongo is configured in `session({ store })`, not merely
  instantiated. Keep the same SESSION_SECRET across restarts. Use HTTPS,
  `cookie.secure=true` in production, and `trust proxy` behind a TLS-terminating
  host proxy. Confirm the sessions collection is accessible in Atlas.

Secure cookie is missing in production
  Verify the public site is HTTPS and `app.set("trust proxy", 1)` runs before
  requests are handled by session middleware.

Image upload fails
  Verify all three Cloudinary variables in the deployment environment, confirm
  the form field is named imageFile, check the 5 MB limit and file type, and
  inspect the Cloudinary response/error in server logs. Keep secrets private.

Search category gives no results
  Confirm the category string matches one of the schema enum values. Existing
  records without categories are inferred from title/description; new listing
  forms should save an explicit category.

Map points to a city or region instead of the property
  This is expected when only a general location and country are stored. Add
  precise coordinates if the product needs exact pins.

Seed command removed live listings
  Stop using the destructive seed script on production. Restore from Atlas
  backup if available, then change the script to target a development-only DB.


16. FINAL REBUILD ORDER AT A GLANCE
----------------------------------

1. Install Node/npm and initialize package.json.
2. Install dependencies and create the folder structure.
3. Create Atlas and Cloudinary accounts and configure environment variables.
4. Build User, Listing, and Review Mongoose models.
5. Implement Cloudinary Multer storage and upload validation.
6. Implement auth, flash, owner checks, MongoStore, and Passport middleware.
7. Connect to Atlas and only listen after the connection succeeds.
8. Implement listing/search/category/review/auth routes.
9. Build EJS layout, navbar search, listing forms/cards/detail, and user forms.
10. Add category filtering, map display, CSS, and form validation.
11. Seed only a development database.
12. Run locally and verify user flows and ownership checks.
13. Configure production environment variables, Atlas network access, HTTPS,
    proxy trust, and deployment start command.
14. Verify every flow on the deployed site.
